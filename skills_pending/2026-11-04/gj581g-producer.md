## The board
`PRODUCTION.md` lives in three places that must match: the channel folder on Sam's computer (`G:\My Drive\Decked out Data\PRODUCTION.md`), the claude.ai project "Youtube Video Creation" (`claude/PRODUCTION.md`), and the working directory while a session runs. Other sessions write to it too: always stage the current G: copy (or read the project copy) and merge your lines into it; never write an older copy over a newer one (it happened several times on 3 Nov). Sections, in this order:
1. **Now** — at most three items, numbered in priority order, each with its next concrete step and any decision waiting on Sam (marked **Decision pending**).
2. **Backlog** — ideas, builds, pilots owed, library stocking, setup tasks. One line each.
3. **Standing decisions (newest first)** — dated, one line, in Sam's words where possible. Rule changes (music, montage, platform clips, screenshots, silent holds, sentence clarity, swearing, second voice), approvals (styles, scripts, characters, voices), workflow rules (clip pipeline, no speed-up, end card). The style library and the skills carry the detail; the board carries the date and the one-line fact.
4. **Hand-off (end of last session)** — what is delivered, what is rendering or waiting, the open decisions, and the first thing to do next time.

## Session start (always)
1. Read `PRODUCTION.md` from the computer when it is linked (stage it), otherwise from the project. If the two differ, the newer one wins; say so in one line.
2. Clone the toolkit and read `toolkit/LESSONS.md`; its guards apply to everything below.
3. In a series, read its bible (`series/<Series>.md` in the project and on G:): the original brief, the arc, the running storyline and the threads to pay off. Update it when a video locks and when it ships.
4. Read the hand-off and the Now list. Check for background work that may have finished (`build/status.json`, `build/build.log`, renders in `out/`).
5. Say in two lines where things stand and what you are about to do. Don't recap the whole board.
6. Open the stage skill the first task needs. ## The workflow (trial from 2 Nov 2026; Sam: watching the script play out is how he gets creative with it)
1. **Research + independent fact-check in parallel:** a separate agent that has not seen the script checks every claim against primary sources while other work runs (on 2 Nov it caught two wrong on-screen claims in the Raise pilot). Research notes are drafts; the fact-check pack is the source of truth. Where measures disagree (e.g. OECD deflator vs CPI), show both. Claims about real people that a joke relies on are fact-checked like any other claim.
2. **Script + storyboard:** every line tagged with `treatment` and `changes` (see `gj581g-scene-quality`), with `say`, `must` and `tight` where the clone needs them (see `gj581g-voice-music-montage`); joke lines tagged with their pattern ID (B01-B30 from `styles/BRITISH_HUMOUR_TOOLKIT.md` in series that use it) and `energy: "dry"`; in videos with the second voice, her lines tagged `who: "heckler"` and `mood`. Run the voice lint on the draft so clone hazards are reworded before Sam reads it; new character names get their clone test here. Run the fresher test (`gj581g-first-lecture`: `python3 toolkit/story/simple_lint.py <script.json>` plus a first-day-student read by a separate agent) on every draft before Sam reads it.
3. **Animatic:** the whole video through `build.py` with `"voice_mode": "kokoro"` (quick computer voice at natural speed, never sped up) and `"render_scale": 0.6667` (720p): real layouts, simple motion, captions; facts not yet cleared are labelled "draft". Sam watches and edits the script freely; iterate. (On Raise_v1 Sam skipped a second animatic and went straight to clips; that's his call each time.)
4. **Punch-up pass** (from 3 Nov 2026): after the facts lock and before the first line is voiced, the numbered punch-up file (`<Topic>_punchup.md`, P1, P2... in two tiers: picture only, new lines) goes to Sam; he approves by ID; his picks go into the script and the storyboard. Picks that arrive after approval go to the next video.
5. **Lock the script.** Nothing goes on screen as fact, and no clone voicing starts, until the fact-check passes (the fact-check CSV, every verdict OK, named in `project.json` as `"factcheck"`) and the fresher test is clean (no `simple_lint` FAIL; the student read's points fixed).
6. **Voice first, then picture** (Sam, 3 Nov 2026: streamline the voice; the clone stays, no faster hardware for now). (a) Voice the whole locked script in one batch in Sam's clone: `build.py full.json --to listen` (voice -> align -> mix -> `<out>_voice.mp3`, the whole narration with the voice finish). Run it in the background as soon as the script locks; on the 2-core workspace it takes a few hours. (b) Sam listens to the MP3 with its automatic listening checklist (build stage `qa`, `toolkit/tts/qa_final.py`; hard faults are fixed before he hears it) and replies by item number ("3 redo, rest fine"); each named line is re-voiced alone and spliced with `toolkit/tts/patch_line.py script.json <voice profile> <takes> LINE_ID` (the neighbouring lines stay exactly as they were), then `--from align` and a new MP3. (c) Then picture, clip by clip: each clip project reuses the approved takes (`build.py clipX.json --from align`), so clips are rendered, never re-voiced; Sam reviews the picture of clip N while clip N+1 renders. The Heckler's lines, if any, are voiced by the same build when `project.json` has `"heckler_ref"` (her own synthetic voice, 1.2x; see `gj581g-voice-music-montage` 0b), so they are in the MP3 Sam approves. Approved clips are never redone; new ideas go to the next video.
7. Music, only if Sam wants it: a sampler after the script is locked; his pick goes into the mix (`build.py --from mix`).
8. **Join** = one render of the whole video from the approved takes, not a stitch of clip files (the `full.json` project, `build.py full.json --from align`), so sound and picture have no seams; at 1080p; captions from `toolkit/story/timing_srt.py <timing.json> <out.srt>` (the caption `text`, timed by the spoken words; the Heckler's lines are left out). Deliver a 720p review copy (bridge-sized) and a 1080p upload file at about 6 Mbps (`-vf hqdn3d=1.5:1.5:3:3 -crf 22 -maxrate 6M -bufsize 12M`: crf alone on the grainy banknote ground made 1.6 GB); the upload file goes to Sam in the chat (it is far over the 30 MB file bridge). **After the join nothing changes in that video** (Sam, 3 Nov 2026); every new idea goes to the next one. Then package, upload, post-publish review.
This replaces the "pilot (45-60 s) -> voice everything -> clips through `v2.py`/`run.py`" sequence, the earlier "voice clip N+1 while Sam reviews clip N" step, and the hand-run `render_chunks.sh` + `assemble.sh` steps described in older text; where they disagree, this section wins. A pilot is still used for a brand-new look or series: it comes before the animatic, its own few lines are fact-checked first (or its figures are labelled "pending"), and only then may it use the clone, with `"factcheck_waiver": "<why>"` in `project.json`. That is the only exception to the clone gate.

## The build (one command)
`toolkit/build/build.py project.json`: voice -> align -> mix -> listen (the narration as an MP3 for Sam) -> qa (`tts/qa_final.py` re-checks the finished file and writes the numbered listening checklist; hard faults stop the build) -> pace lint -> render -> frame check -> deliver; `--to STAGE` stops after a stage (`--to listen` for the voice-first review). `"voice_mode"`: `kokoro` for the animatic (add `"render_scale": 0.6667` for 720p), `scene` for Sam's clone, `line` for single-line fixes. Clone modes refuse to start without `"factcheck": "<csv>"` whose every verdict is OK (or a pilot's `"factcheck_waiver"`) and without a clean voice lint (or `"voice_lint_allow"` for approved lines). The mix applies the voice profile's finish (`post_fx`, Sam's option B). The check stage fails if any line's last word is silent. Resumable (`--from STAGE`, `--only STAGE`, `--lines ID ...` to re-voice only those scenes in scene mode or lines in line mode, always last on the command line; `SEED_OFFSET=n` for fresh takes): `--from mix` after music or sound changes, `--from render` for picture-only changes. Writes `build/status.json` and `build/build.log`, refuses to start while another voice or render job runs. It runs only the pace lint; run `scene_lint.py`, `cue_lint.py` and `simple_lint.py` yourself. It voices the Heckler's lines as their own units (`H_<id>`) when `project.json` has `"heckler_ref"`. Look at `build/frames_sheet.png` and the frames the narration names before sending anything.

## Engineering guards (each one cost time on 2-3 Nov 2026; details in LESSONS.md)
- One voicing process per scene or line: Chatterbox + Whisper in one long process is OOM-killed (exit 137); long scenes are voiced in parts that resume after a kill.
- Pace-only failures stop after 3 tries (`PACE_TRIES`) and keep the least rushed take: on Raise_v1 lowering cfg fixed only 4 of 71 rushed takes, and 213 of 388 takes failed on pace alone (8.8 hours of voicing). Words that must be heard and tight phrases still get all 8 tries.
- A single bad line is patched (`patch_line.py`), never by re-voicing its whole scene.
- Never voice and render at the same time.
- Never `pkill -f` or `pgrep -f | kill` a pattern that appears in your own command line (it kills itself, exit 144; again on 3 Nov); stop jobs with the task-stop tool or by PID: `ps aux | grep "[c]bmood" | awk '{print $2}'`.
- Wait for background work on a PID (`kill -0`) or an explicit DONE marker, never on "the log has a line". Don't watch a long job with a monitor that reports every progress line; report only DONE and failures.
- When a scene needs re-voicing, stop the build before render so no render is wasted.
- Run long jobs with the tool's background mode (not `&`), and watch them with a monitor whose filter also matches failures (Traceback, Killed, FAIL, exit).
- Commit and push every toolkit change before ending a turn (`git pull --rebase` first: other sessions push too). LESSONS numbers are shared across chats: pull first and take the next free number.
- When a skill says a tool does something, the tool must really do it: the 2 Nov audit found the skills describing an animatic mode and a fact-check gate that `build.py` didn't have (both added); the 3 Nov audit found "the Heckler is never subtitled" in the skills while `timing_srt.py` and `Captions` still showed her (both fixed). Change the tool or the text, never leave them apart.

## Choices that go to Sam (and those that don't)
- **Voice and music:** short A/B samplers, with Sam's real recording or the narration as the reference; never pick music unheard. Second voices: a sampler of candidate voices first, then the chosen one with its moods, at the speed Sam picks.
- **New recurring characters:** a sheet of at least 10 designs in different drawing manners, then the pick's mood sheet and an in-frame mock (see `gj581g-scene-quality`). Sam picks.
- **Look, scenes, visuals, placement:** Claude decides as creative director (Sam's standing instruction) and says in a line what was chosen and why. One exception: a chart look other than dot-matrix, people icon arrays or the series' own chart style goes to Sam first.
- **Jokes:** the punch-up file, approved by ID.
- **The narration:** the voice-first MP3 with its listening checklist, reviewed by Sam by item number and approved before any picture is rendered.
- **Facts:** never Sam's job to catch; the independent fact-check does it.

## During the session
- When Sam decides something that will still be true next month, add a dated line to Standing decisions in the same turn (and, if it is a channel rule, to the channel-wide rules in `STYLE_LIBRARY.md`; if it is about a series, to its bible; if it changes how a stage works, propose the skill change too, to every skill it touches).
- When Sam flags a problem, or a build fails for a new reason, add a line to `toolkit/LESSONS.md` (mistake, root cause, guard) and fix the same kind of problem everywhere it occurs.
- When a deliverable lands (a clip approved, a video joined, packaging sent), move the item on the board and name the next step.
- Keep the Now list at three. Anything else goes to the backlog.
- **Sam works in more than one chat.** Before a milestone that freezes something (locking a script, approving the narration or a clip, the join, packaging), re-read the board and the bible for decisions made elsewhere since this session started, and raise any conflict with Sam before acting (3 Nov: punch-up picks made in another chat after clip D's approval were found only after the join).
- **Writing the board:** never overwrite it blindly. Stage the G: copy, diff it against yours, merge (keep every line other sessions added), write it to G: and the project, then list G: again and check the size. Google Drive put older copies back several times on 3 Nov 2026.
- Every deliverable goes to the chat (SendUserFile) and the computer (device_commit_files, under 30 MB) when linked; the board notes where it is.
- If the conversation is long, write the hand-off early (after each milestone), not only at the end: compaction can drop anything not written down (on 1 Nov 2026 the two-video option list was lost this way).

## Session end (or when Sam goes quiet after a milestone)
1. Write the hand-off: delivered, in progress (with the background job and the file it will produce), open decisions, first step next time.
2. Save `PRODUCTION.md` to the computer and the project; commit and push the toolkit.
3. Reply in two or three lines: what is done, what is waiting on Sam.

## Review cadence
- **Per video, after publishing (the post-publish review):** 7 and 28 days after upload, read the YouTube Studio retention curve in the built-in browser, note the three biggest drops with their timestamps against the storyboard's retention map, and add one line to the project log and one to the backlog if a pattern needs a rule. Log Test & Compare thumbnail winners in `styles/THUMBNAIL_LIBRARY.md`. The audience's curve is the only feedback that isn't our own opinion.
- **After any change to the skills:** an independent reviewer (an agent that didn't write the change) reads all thirteen channel skills and their reference files in full and lists clashes (numbers, owners, workflow order, stale text, commands the toolkit doesn't support), ranked by severity; fix the real ones in the same turn and propose every changed skill.
- **Weekly:** the niche scout (`gj581g-niche-scout`) and the peer watch (`gj581g-peer-watch`); **daily:** the scout's `alert.py`, silent unless something big moved. These can be scheduled tasks if Sam wants them.
- **Per month:** a workflow audit like the one on 1 Nov 2026: list the errors and delays of the month (from `LESSONS.md`), the root cause of each, and the guard added; prune the backlog; confirm the three Now items; run the cross-skill clash audit.

## What this skill does not do
It does not pick visuals, write scripts, voice, render or package; it does not create tasks in outside apps (the board is the task list); it does not ask Sam questions the board already answers.
